Decisões Arquiteturais (ADRs)

Escolhas técnicas fundamentais com justificativa e trade-offs

01
Objetos customizados vs. Cases nativos
Decisão
Objetos customizados (Pedido_Compra__c, etc.) em vez do objeto Case nativo
Justificativa
O processo é gestão de pedidos com linhas de SKU, checkpoints temporais e escalonamento estruturado — não suporte ao cliente. Usar Case forçaria workarounds e geraria dívida técnica ao escalar para o OMS.
Trade-off
Maior esforço de configuração inicial; escalation rules nativas não disponíveis (constrói em Flow)
02
DigiBee como única camada de integração
Decisão
Toda integração SF ↔ sistemas externos passa pelo DigiBee. Nenhuma integração direta SF ↔ SAP
Justificativa
DigiBee é o barramento corporativo do Itaú — centraliza controle de erro, retry, monitoramento e governança. Alinhado ao padrão do banco.
Implicação
Contrato de integração deve ser definido com equipe DigiBee/SAP antes do desenvolvimento
03
Experience Cloud — apenas fornecedores/fabricantes
Decisão
Experience Cloud somente para fornecedores/fabricantes (~90). Fiscais usam o Portal de Reservas Angular — NÃO migram para SF.
Justificativa
São públicos distintos: fornecedores reportam status de produção (novo portal); fiscais gerenciam reservas de obras (portal existente, em evolução). Migrar o portal de reservas não traz ganho proporcional.
Risco
Modelo "usuário gest" para fornecedores precisa de aprovação COI/Segurança. Validar integração com Rainbow/Parcerias — plataforma corporativa de habilitação de terceiros do Itaú.
04
Org único (mesmo da Manutenção)
Decisão
Implementar no mesmo org Salesforce que já roda o módulo de manutenção
Justificativa
Reduz custo de licença, simplifica integrações futuras entre módulos e viabiliza visão 360° da agência (obras + manutenção + compras).
Pré-requisito
Análise do estado atual do org antes de iniciar (namespace, limites de metadados, customizações existentes)
05
Portal de Reservas permanece em Angular/AWS
Decisão
O Portal de Reservas (Angular/AWS) não será migrado para Salesforce. Será integrado via DigiBee na Fase 2.
Justificativa
Portal já está em produção com evolução planejada (manutenção, equipamentos, acionamento). Migrar = retrabalho sem ganho proporcional. Integração via DigiBee entrega os dados sem perder o que foi construído.
Integração (Fase 2)
Portal Reservas → evento → DigiBee Pipeline → SF REST API → Upsert Reserva__c + Acionamento__c
06
TMS B2B externo ao Salesforce
Decisão
O TMS B2B (sistema de gestão de transporte para agências) será construído fora do Salesforce. SF alimenta via DigiBee.
Justificativa
TMS B2B não existe ainda. O CB4 (TMS B2C) é a referência arquitetural. Consolidador de cargas, cotador de frete e gerenciador de entregas são capacidades específicas de transporte, fora do core do Salesforce.
MVP (Fase 3)
E-mail/template para transportadoras como primeiro passo. Integração Intelpo (homologada) para carriers tradicionais.
07
Salesforce responde à pergunta aberta do TO-BE sobre portal de compras
Contexto
O TO-BE v20260911 registra como pergunta aberta: "Qual portal usaremos para realizar a compra do material e acompanhar a produção/entrega?" — confirma que esta lacuna ainda não estava preenchida.
Decisão
Salesforce (Fase 1) é a resposta para essa pergunta aberta — cobre compra + acompanhamento de produção com fornecedores + visibilidade de entrega para analistas internos.
Impacto
O OMS [AWS] resolve o lado da demanda (priorização de reservas). O Salesforce resolve o lado da oferta (gestão de compras). São complementares — não concorrentes.

Arquitetura de Integração

DigiBee como barramento único — SAP ECC e AGV WMS

SAP ECC → Salesforce
SAP ECC └─ IDoc / RFC (criação/atualização de PO) └─ DigiBee Pipeline ├─ Transformação: campos SAP → REST SF ├─ Enrich: resolve AccountId por CNPJ ├─ Enrich: Motor Alocação → fornecedor designado ├─ Retry automático em falha └─ Salesforce REST API └─ Upsert: Pedido_Compra__c (ext. ID: Numero_PO_SAP__c)
OAuth 2.0 · JWT Bearer Flow

Transações de origem: ME51N / CN22 / MB21 / W31 / W32 → campo Tipo_Transacao_SAP__c

Sistema AGV (WMS físico) → Salesforce
Sistema AGV // WMS físico Cajamar └─ Arquivo FTP (a cada 3h) └─ DigiBee Pipeline ├─ Parse do arquivo de estoque └─ Salesforce REST API └─ Update: Product2 Saldo_Estoque__c por SKU
3h · Bulk API 2.0 recomendado

WMS Itaú [AWS] ≠ Sistema AGV — duas camadas: WMS Itaú = estoque lógico (em construção); AGV = estoque físico. Fase 2: saldo lógico via WMS Itaú API.

Arquitetura de Automação

Flows nativos + Apex restrito a onde Flow não alcança

Mapa de Flows

FlowTipoTriggerResponsabilidade
PedidoCompra_OnCreateUpdate Record-Triggered Criação ou alteração de Data_Entrega_Prevista__c Cria / recalcula Checkpoints; invoca Apex de criticidade
Checkpoint_Scheduler Scheduled A cada hora Processa checkpoints vencidos; cria Escalations; suprime quando slot AGV confirmado
Escalation_Escalator Scheduled A cada hora Verifica SLA de Escalations abertos; sobe nível se SLA vencido
Score_Criticidade_Diario Scheduled Diário (madrugada) Recalcula Score_Criticidade__c para todos os pedidos em aberto
Portal_AcaoFornecedor Record-Triggered Atualização via portal Fecha Checkpoint relacionado; notifica analista responsável
Apex — uso restrito

Apex é necessário apenas onde Flow não consegue expressar a lógica:

CriticidadeScoreCalculator (Invocable)
Cálculo multi-campo cruzando Criticidade__c + Saldo_Estoque__c + reservas abertas — loops e comparações que explodem em Flow


CheckpointRecalculator (Invocable)
Delete + re-create dos Checkpoints pendentes quando data muda — operação DML em coleção mais segura em Apex

Email-to-Case

Caixa dedicada configurada como Email-to-Case


Roteamento: extrai Numero_PO_SAP__c do assunto → vincula ao Pedido_Compra__c


Flow pós-criação: analisa corpo do email → atualiza Checkpoint__c se conteúdo identificável


⚠️ Email-to-Case usa objeto Case internamente — requer mapeamento customizado para vincular ao Pedido_Compra__c. Avaliar com equipe de desenvolvimento.

Princípio de automação: Tudo que é fluxo, notificação, criação de registros relacionados e atualização de status é construído em Flow nativo. Apex é invocado pelo Flow somente para operações que exigem lógica complexa ou DML em coleções — mantendo rastreabilidade e reduzindo dívida técnica.

Portal de Reservas — Opções de Arquitetura

Decisão pendente: manter Angular/AWS integrado ou reconstruir em Experience Cloud

Contexto: O Portal de Reservas (Angular/AWS) já existe, está em produção e tem roadmap de evolução ativo. Há duas opções arquiteturais com trade-offs distintos para a integração com Salesforce.
Opção A

Manter Angular/AWS e integrar via DigiBee

Recomendada para Fase 2
Fluxo de integração
Portal de Reservas (Angular/AWS) ├─ Cria reserva/acionamento │ └─ DigiBee Pipeline │ └─ SF REST API │ └─ Upsert Reserva__c ├─ Cancelamento/reprogramação │ └─ DigiBee → SF update Status └─ Consulta resultado OMS (opcional) └─ DigiBee ← SF priorização // Salesforce (interno) Reserva__c criada → Flow → classifica tipo + estado Motor OMS processa → S&OE alimentado em tempo real
Prós

✓ Portal já existe e em produção

✓ Time com roadmap ativo (manutenção, equipamentos)

✓ Sem rebuild — menor risco de interrupção

✓ Sem licença Experience Cloud para fiscais

✓ Caminho mais rápido para Fase 2

Contras

✗ Dois sistemas a manter (Angular + SF)

✗ Dados replicados — governança dividida

✗ Fiscal não vê status SF em tempo real sem API de consulta

✗ Nova feature exige coordenação entre dois times

Opção B

Reconstruir em Salesforce Experience Cloud

Considerar Fase 3+
Fluxo de integração
Experience Cloud (LWR Site — fiscais) ├─ Fiscal faz login (usuário gest) ├─ Cria Reserva__c diretamente na org ├─ Record-Triggered Flow → imediato ├─ OMS e S&OE processam em tempo real └─ Fiscal vê status completo no portal // Integrações mantidas SF → DigiBee → SAP ECC // substitui JSON às 19h do Angular EAM → DigiBee → SF // catálogo SKU, inventário agências
Prós

✓ Plataforma única — sem duplicidade de dados

✓ Automações SF disparam em tempo real

✓ Arquitetura mais simples a longo prazo

✓ Fiscal vê visibilidade total do status

✓ OMS sem dependência de time Angular

Contras

✗ Retrabalho — jogar fora o que foi construído

✗ Rebuild de todas as regras de negócio (40 dias, limites SKU, validações)

✗ Integração SF→SAP via DigiBee precisa ser construída

✗ Licença EC para todos os fiscais (podem ser 100–300+)

✗ Aprovação COI/Segurança para acesso de terceiros

Comparativo de decisão

CritérioOpção A — Manter AngularOpção B — Experience Cloud
Tempo para Fase 2 Menor — portal existe Maior — rebuild necessário
Custo de licença Sem adicional Experience Cloud × nº fiscais
Manutenção longo prazo Dois times, dois sistemas Um time, uma plataforma
Flexibilidade OMS Depende de API entre sistemas Nativa — dados no mesmo org
Risco de migração Baixo Alto — features + SAP integration
Visibilidade do fiscal Limitada — precisa de API de consulta Completa em tempo real
Recomendação ✓ Fase 2 — caminho mais rápido Fase 3+ — se Angular travar evolução
Posição do arquiteto Salesforce: A Opção A é recomendada para a Fase 2 — preserva o investimento existente, não bloqueia o OMS e tem menor risco. A Opção B deve ser revisitada quando o portal Angular se tornar um gargalo de evolução ou quando os custos de manutenção de dois sistemas superarem o custo de reconstrução. O ponto de decisão natural é após 12–18 meses de operação com ambos integrados. Ponto crítico: levantar o número real de fiscais ativos (terceiros) antes de avaliar o custo de licença da Opção B.

Dependências Críticas

Itens que bloqueiam o início ou o progresso do desenvolvimento

🚫
BLOCKER

Taxonomia canônica de entidades

O que é "pedido", "reserva", "intervenção", "demanda" — diferentes sistemas usam termos diferentes. Deve ser definido antes de qualquer modelagem de dados.

Responsável: Arquitetura do banco + equipe operacional (Cássio, Guilherme)
🚫
BLOCKER

Contrato de integração SAP ↔ DigiBee

Payload, campos obrigatórios, evento de trigger. Incluir obrigatoriamente: transação SAP de origem (ME51N/CN22/MB21/W31/W32), Código UPE da obra. Alterações após início geram retrabalho no modelo.

Responsável: Equipe SAP + DigiBee + Arquiteto SF
⚠️
HIGH

Governança de acesso Experience Cloud + Rainbow/Parcerias

Modelo "usuário gest" para fornecedores precisa ser validado com COI e Segurança. Adicionalmente, validar se o Rainbow/Parcerias (plataforma corporativa de habilitação de terceiros) pode ser base de provisionamento do acesso ao portal SF — evita duplo cadastro.

Responsável: COI + Segurança Itaú + Time Rainbow + Product Owner
⚠️
HIGH

Alinhamento com OMS [AWS] — qual API o OMS expõe para a Mesa de Decisão SF?

Na Fase 2, a Mesa de Decisão S&OE no Salesforce precisa consumir dados do OMS [AWS] (dilemas, priorização, disponibilidade) via DigiBee. O contrato de API deve ser definido em conjunto com o time de produto AWS e o Arquiteto SF.

Responsável: Time produto AWS + Arquiteto SF + Product Owner
⚠️
HIGH

Questão aberta C1: Baixa no SAP — quando?

O Diagrama C1 aponta: "faz sentido dar baixa no SAP? se sim, quando? na solicitação de separação?" — decisão pendente. Define o trigger da integração write-back para Fase 2.

Responsável: Arquitetura + SAP + equipe operacional
⚠️
HIGH

Questão aberta C1: Geração de DC-e para reversa — quando?

O Diagrama C1 aponta: "em que momento devemos gerar DR pra logística reversa?" — decisão pendente. Impacta o design do fluxo de reversa e a integração com o Gerador de DC-e [AWS].

Responsável: Arquitetura + Time TMS/AGV + equipe operacional
⚠️
HIGH

Análise do org Salesforce existente

Estado atual do org de manutenção (namespace, limites de metadados, customizações existentes) pode revelar restrições que alteram decisões arquiteturais.

Responsável: Arquiteto SF + Admin do org (Fabian)

MEDIUM

Disponibilidade do WMS Itaú [AWS]

O WMS Itaú (estoque lógico) ainda não existe — é uma plataforma AWS em construção pelo time Itaú. O motor de priorização do OMS depende deste sistema. Define o ritmo da Fase 2.

Responsável: Time de plataforma AWS Itaú + Liderança

MEDIUM

Integração EAM (Attune) → SF na Fase 2

O EAM (produto: Attune, gerenciado pela área GIMEA) fornece catálogo de SKUs e inventário de agências. Na Fase 2, esses dados enriquecerão os registros SF. API ou DigiBee pipeline a definir.

Responsável: Time EAM/GIMEA + Arquiteto SF

MEDIUM

Formato e campos do arquivo FTP da AGV

Necessário para mapear o pipeline DigiBee de sincronização de estoque. Impacta apenas o módulo de Score de Criticidade.

Responsável: Time AGV + Arquiteto SF

MEDIUM

O Acelera estava construindo partes do OMS e integração TMS. Com a reestruturação, há risco de retrabalho ou conflito de escopo. Requer alinhamento antes do início.
